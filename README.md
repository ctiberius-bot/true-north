# True North Citadel

Current release: `2.3.37-2026-10-09`. Each explicit authenticated GUI Generate action creates one exact authorization bound to the selected job, listing version, and Career Arsenal. The model selects exact evidence pairs; server rendering preserves each source's factual actor/action/outcome statement and adds a separate role-relevance sentence. Resume facts are placed beneath their actual employers. Compact prompt evidence is never used for final rendering; full verified source text controls the stored artifact. Raw or truncated excerpts, citation identifiers, placeholders, duplicate evidence, unsupported ownership claims, and attribution inflation are rejected. The fixed package ceiling and monthly runaway cap remain enforced; drafts remain private and unreviewed, with no automatic submission.

## Authenticated listing capture bridge

Workers never inherit a Chrome login. A user-authenticated external Chrome operator may POST only visible listing evidence to `POST /api/browser-captures/listing` using the existing True North dashboard session. The strict payload is `job_id`, `source_url`, `captured_at`, `availability` (`open`, `closed`, or `inaccessible`), and, only for an open listing, the visible `full_description` plus optional title/company/location/engagement/external ID. Cookie, password, token, header, or arbitrary extra fields are rejected.

Each check is timestamped and versioned in D1. An open capture is fresh for 15 minutes. Chris approval requires that exact listing version; the `approved_to_send` readiness transition requires another fresh open check. Changed content revokes prior package approval; closed or inaccessible listings remain blocked. Since this bridge depends on an available authenticated external Chrome session, unattended recurring access is not guaranteed.

The project retains every supported job-alert card, discovery link, and unclassified provider candidate; researches each full listing; deduplicates evidence-backed jobs; assesses them against selectable role profiles and the versioned Career Arsenal; and produces a **cleanup preview** only.

## Safety boundary

- No automatic sending, job application, Gmail mutation, cleanup mutation, paid-tool purchase, or schedule activation. Production AI generation is disabled.
- Cleanup is structurally restricted to `mode='preview'`; there is no Gmail write implementation and Trash is never purged.
- Human recruiter, application, and interview threads are protected. Any blocked, login-required, retrying, unreconciled, or unverified message is ineligible.
- Tokens do not belong in D1. Production activation requires state + PKCE, encrypted platform secrets/token brokering, and mailbox binding to `ctiberius@gmail.com`.
- The Career Arsenal is read-only evidence. Store its version/hash, source anchors, and claim tags; propose new evidence to a review queue rather than editing the master.

## Implemented runtime

- D1Repository persists messages, replayable parser snapshots, quarantined candidate links, discovery checkpoints, observations, research tasks, canonical jobs, listing versions, evidence, runs, selectable versioned profiles, a derived read-only Career Arsenal index, assessments, cleanup-preview outbox records, coverage, and audit-ready state.
- `GmailReadOnlyAdapter` uses an injected access-token provider, verifies the mailbox profile, paginates the real Gmail `messages` response, uses a 48-hour query overlap, strictly allowlists automated alert senders from the six selected sources before persistence, checks thread metadata for human/application/interview signals, fetches full candidate messages, and decodes HTML MIME parts. It contains no OAuth grant or Gmail-write implementation.
- Bounded intake accepts aligned DKIM identity from either `Authentication-Results` `header.d` or Gmail's `header.i` identity. `header.i` is parsed as a complete strict identity and its domain is taken only after the last `@`; when `header.d` is present, both identities must be consistent within the same passing DKIM clause and aligned to the exact provider domain or its subdomain. Each inspected message produces only a truncated SHA-256 reference, result, allowlisted source when known, and a fixed reason code; aggregate skip reasons and those safe records are stored in the run counts. Bodies, subjects, sender addresses, authentication headers, tokens, and URLs are excluded from this diagnostic metadata.
- `PublicListingAdapter` accepts only configured provider hosts, fetches read-only public HTML, extracts full `JobPosting` JSON-LD evidence, walks `rel=next` discovery pages to exhaustion within a configured safety bound, and records `login_required` or retry states rather than claiming completion. Ladders supports only the exact HTTPS `t.ladders.co` initial redirector; every hop rejects credentials, non-HTTPS schemes, nonstandard ports, IP literals, and unapproved hosts, while final content remains restricted to `theladders.com` or its subdomains. Legal, unsubscribe, contact, and social-navigation anchors never become runnable tasks.
- Manual bounded research may select one exact allowlisted provider with `POST /api/run/research?limit=5&source=jobright`; provider selection changes only runnable-task selection and does not rewrite, retry, or otherwise mutate another provider's queue.
- The responsive private dashboard has authenticated APIs for Arsenal indexing, exact listing-version/content-hash assessment provenance, cleanup preview, read-only intake and research, queue recovery and pagination, researched-job evidence and assessment detail, and creation or activation of versioned role profiles with compensation, geography, engagement, relocation, title, and exclusion controls. Cleanup reconciliation counts source observations separately from discovery children, treats zero-link parsing as unverified, and requires a completed evidence-backed research path for every source observation. Cleanup remains preview-only, and scheduling is disabled.
- Authenticated runtime and GUI workflows persist sourced company dossiers; final Critic fit reviews; evidence-mapped Writer packages; enforced Writer → Critic → Chris review transitions; pipeline stage/next action; scheduled interviews; sourced interviewer dossiers; prep, practice, psych-brief, and debrief records; Coach plans; and isolated private non-clinical Doc sessions. Chris package approval, `chris_approved` interview records, and release of private Doc insights require server-side password reauthentication. Revoking an approved package automatically demotes any `approved_to_send` pipeline item. Employer-facing packages reject `internal_only` Arsenal claims. The Worker never sends or applies. The reviewed offline operator receipt builder can emit a guarded receipt statement only after exact GUI approval, a live claim, real external submission, and visible same-host confirmation; its evidence remains operator-observed, not cryptographic employer proof.
- The offline v2.2 repair uses the native Cloudflare Workers AI binding with `@cf/meta/llama-3.3-70b-instruct-fp8-fast`, without an API key or AI Gateway. It supports only one concise outreach draft (maximum 800 characters), with `stream:false`, `max_tokens:900`, and a strict JSON Schema response contract. It selects at most 10 bounded, job-relevant exportable sources from the exact listing version, listing evidence, evidence-complete dossier sources, requirements, and non-internal claims from the immutable Drive-master Arsenal version. Source strings are treated as untrusted evidence and embedded commands are ignored. Every generated section must cite exact supplied claim IDs and anchors. Full resumes and every other artifact type fail closed before budget reservation or provider invocation. Results are stored only as `draft_unreviewed`, require human review, and have no send/apply path. `AI_GENERATION_ENABLED` defaults to `false`, and the disabled check occurs before budget reservation or provider invocation.
- The application ledger has a fixed monthly limit of `1,000,000` microdollars ($1) and assumes no free allowance. Each dispatched call atomically reserves and permanently debits a fixed `10,000` microdollars ($0.01), including provider failure or unknown usage; there are no refunds or retries. Input selection is refused unless the UTF-8 prompt estimate plus 4,096 overhead tokens and 900 output tokens fits the 24,000-token context window. Conservative validation rates of $0.294/M input and $2.254/M output keep the configured ceiling below the fixed reservation; reported usage above the reservation rejects the draft. Replays and concurrent settlers cannot debit twice, and inference is refused before the provider call when the application ledger would exceed its limit. This remains an application safety ledger, not a guaranteed provider billing cap, so AI stays disabled pending independent billing validation.

No further call to that model is permitted. This repair uses an officially JSON-Mode-capable alternative and has made zero model calls.

## Private Gmail OAuth deployment

The test deployment uses a private internal Worker, `true-north-citadel-oauth-core`, with no public route and a SQLite Durable Object named `OAuthCoordinator`. Citadel reaches it only through the `GMAIL_TOKEN_PROVIDER` service binding. The exact Google redirect URI is `https://true-north-citadel.ctiberius.workers.dev/oauth/google/callback`.

Authorization is limited to exactly `gmail.readonly`. The flow uses state, PKCE S256, authenticated initiation, a short-lived HttpOnly cookie binding both the browser nonce and initiating Citadel session hash, atomic single-use state consumption, mailbox verification for `ctiberius@gmail.com`, AES-256-GCM encryption before grant storage, refresh-token rotation, and revoked-grant fail-closed handling. The initial token response must explicitly report exactly the requested scope; missing or expanded scopes are rejected. Google refresh responses may omit `scope` when unchanged, so omission is accepted only for a previously verified exact-scope grant; any reported refresh scope must still match exactly. `OAUTH_CLIENT_ID` is public configuration. `OAUTH_CLIENT_SECRET` and a 32-byte `TOKEN_ENCRYPTION_KEY` remain Cloudflare secrets. The exact read-only Gmail grant is connected through the private broker. Scheduling and Gmail mutation remain disabled.

The authenticated dashboard status reads the encrypted server-side grant record through the private service binding and reports only whether the connection is usable, the verified account email, the exact scope, and a safe state. It does not infer readiness merely from Google consent and never returns token material.
